# 开发顺序

> **原语**：本项目沿用的创世叙事词汇，仅用于命名与溯源。
> **工程理解词语**：将原语翻译为可精确执行、可验证的工程术语；本文正文一律使用工程理解词语，原语仅在《术语对照表》中保留。
> 术语对照见 `传承殿/00-宪法/术语对照表.md`。

> **元治理·开发顺序**——按因果链由基础设施到高层，10 阶段推进。

## 一、设计原则

### 1.1 三大铁律

1. 先基础设施再高层——上层依赖下层；下层未完成上层不动
2. 因果链优先——每阶段都是下一阶段的必要前提
3. 每阶段有 falsifiable——阶段完成 = 全部 falsifiable 通过

### 1.2 高效代码 4 条

- 一次改 1-2 个文件，不批量
- commit message 简洁（< 200 字符）
- 复杂逻辑必须有决策锚注释
- 命名哲学推导，不借词

### 1.3 高效开发 4 条

- 先入稿再落码（AGENTS 强制规则 13）
- 一次跑通 1 步再走下一步
- 不重复造轮子（用现有 crate）
- 早 commit（每阶段必有 1 个可回滚 commit）

### 1.4 安全质量 4 条

- 完整验证流水线 17 项必过
- 概念测试 > 实现测试
- decided_by 必填（不可伪造）
- 历史记录不改（frozen outcome）

### 1.5 整洁整齐 4 条

- 命名纪律（不沿用借来的词）
- 注释规范（5 类型 + 10 禁区）
- 垃圾清理（4 时机）
- 完整验证流水线 + grep 借来词

## 二、10 阶段开发顺序

目标：建立可编译 + 可验证 + 可回滚的基础。

- cargo build 成功
- bash 一键全验.sh 跑通

falsifiable：

## 四、Commit 节奏

### 4.1 每阶段必有

- 阶段开始：1 个 commit（phase start: {阶段名}）
- 阶段中间：每个核心抽象 1 个 commit
- 阶段结束：1 个 commit（phase end: {阶段名} + falsifiable 验证）

### 4.2 Commit message

```
feat(记忆承载): 36 上下文槽位三维正交数据模型

实现 6 分区 × 6 子槽 + 3 档投影 + 3 源记录。
关联决策：260826-2210-4-分类抽象 + 260826-2220-治理-司衡

falsifiable: 36 上下文槽位利用率 ≥ 80%
```

### 4.3 PR 节奏

- 每个阶段 1 个 PR
- 每个 PR 含决策文档（新增/更新）
- 每个 PR 通过完整验证流水线 17/17

## 五、并行开发规则

### 5.1 可并行

- 阶段 2 内：事件流 + 插件上下文（不同 crate）
- 阶段 3 内：6 分区各自测试
- 阶段 7 内：LLM 连接 + 工具循环（不同 crate）

### 5.2 不可并行

- 阶段 4 与阶段 3（决策契约依赖记忆数据模型）
- 阶段 5 与阶段 6（4 分类必须先稳定再跑 e2e）

### 5.3 撞车责任

- 优先序：先开工的优先（按 commit 时间）
- 撞车时：后者主动避让前者
- 撞车后：前者不动，后者等前者 commit 后再继续

## 六、安全 + 质量红线

### 6.1 不可违反

- 不擅自修改 13 条红线（接 02-概念/规则注册表/）
- 不擅自 commit 世界自转产物
- 不擅自动 AGENTS 禁止条款边界内容
- 不替项目负责人拍板

### 6.2 必过门禁

- 完整验证流水线 17/17
- cargo clippy --workspace -- -D warnings 零警告
- cargo test --workspace --lib 全绿
- 所有决策文档带 decided_by + falsifiable + implements
