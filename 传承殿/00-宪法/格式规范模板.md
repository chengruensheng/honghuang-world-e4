# 格式规范模板

> **原语**：本项目沿用的创世叙事词汇，仅用于命名与溯源。
> **工程理解词语**：将原语翻译为可精确执行、可验证的工程术语；本文正文一律使用工程理解词语，原语仅在《术语对照表》中保留。
> 术语对照见 `传承殿/00-宪法/术语对照表.md`。

> **元治理**——所有知识库文档的格式契约。

## 一、文档结尾规范（强制）

### 1.1 通用文档结尾

```
*传承殿 · YYYY-MM-DD · decided_by: {人类标识符}*
*implements: {哲学锚}*
*falsifiable: {可证伪命题 + 时间窗口}*
```

### 1.2 决策文档结尾

```
*YYMMDD-HHMM-{slug} · 传承殿 · YYYY-MM-DD · decided_by: {人类标识符}*
```

## 二、概念文档结构（02-概念/）

每份概念文档必须有三层：

```markdown
# NN-{概念名}.md

> **概念·方法论原则**——{一句话本质}。

## 一、哲学层（为什么）

{为什么需要这个概念}

## 二、概念层（是什么）

{这个概念的本质、三条铁律、与相似概念的区分}

## 三、工程层（怎么实现）

{数据模型、接口契约、依赖关系}

---

*传承殿 · YYYY-MM-DD · decided_by: {人类标识符}*
*implements: {哲学锚}*
*falsifiable: {可证伪命题 + 时间窗口}*
```

## 三、决策文档结构（03-决策/已定/）

每份决策文档必须有 YAML 头 + 8 个字段：

```markdown
---
id: YYMMDD-HHMM-{slug}
title: {一句话决策标题}
stage: {1/3 提案 | 2/3 审阅 | 3/3 拍板}
decided_by: {人类标识符}
falsifiable:
  - 命题: {可证伪命题}
    证伪方法: {机械判定 | 人工统计 | 文档审查}
    时间窗口: {N 个月}
upstream: {上游决策 id 或 N/A}
implements: {哲学锚}
decided_at: {YYYY-MM-DD}
---

## 背景

{为什么需要这个决策}

## 方案

{具体方案 + 备选方案 + 不采纳理由}

## 后果

{正面后果 + 代价与风险}

---

*YYMMDD-HHMM-{slug} · 传承殿 · YYYY-MM-DD · decided_by: {人类标识符}*
```

### 3.1 决策契约必填字段

| 字段 | 必填 | 说明 |
|:--|:--|:--|
| id | ✓ | YYMMDD-HHMM-slug，slug 必须唯一 |
| title | ✓ | 一句话，不超过 30 字 |
| stage | ✓ | 1/3 / 2/3 / 3/3 |
| decided_by | ✓ | 人类标识符（不能是 LLM） |
| falsifiable | ✓ | 至少 1 条可证伪命题 |
| upstream | ✓ | 上游决策 id 或 N/A |
| implements | ✓ | 哲学锚 |
| decided_at | ✓ | YYYY-MM-DD |

## 四、设计文档结构（04-设计/）

每份设计文档必须有：

1. **数据模型**（如适用）：Rust struct 定义
2. **接口契约**：trait 定义
3. **依赖关系**：入稿点（引用其他文档）

## 五、治理文档结构（06-治理/）

每份治理文档必须有：

1. **承接机制**：5 基线 / 4 禁止 / 元三治 的具体实现
2. **可证伪条件**：每条机制都有 falsifiable

## 六、哲学锚清单

`implements` 字段必须引用以下之一：

### 6.1 六柱石（道-法-术-鉴-应-元）

- **架构根本**：因果必然性
- **方法论原则**：方法论原则
- **工程实现**：工程化展开
- **检验**：检验主张
- **应变**：居中不动以应万变
- **元治理**：治理的治理

### 6.2 五法（收敛五法）

- **尊重因果顺序**：尊重因果方向
- **恰到好处**：收敛恰到好处
- **明确边界**：知道不做什么
- **定向调节**：损有余补不足
- **力度适配阶段**：力度适配场景

### 6.3 元三治

- **核心规则修改需人类确认**：核心规则修改需项目负责人确认
- **分类不增不减**：4 分类不增不减
- **核心逻辑不绕过检验**：核心算法不绕过检验

## 七、命名规范

### 7.1 目录与文件

- 目录：`00-宪法/` `01-哲学/` ... 用两位数前缀
- 概念文档：`NN-{概念名}.md`（NN 是 2 位序号）
- 决策文档：`YYMMDD-HHMM-{slug}.md`
- 文件名连字符（`-`），模块名用下划线（`_`）

### 7.2 命名纪律（AGENTS § D. 命名规则）

1. **不沿用借来的词**——每个命名必须能回答「为什么叫这个」
2. **哲学推导优先**——每个概念先哲学 → 概念 → 工程
3. **中文标识符**——目录 + 文件名 + Rust 标识符

## 八、哲学推导结构

每份概念文档（02-概念/）的哲学层 → 概念层 → 工程层：

```
哲学层（为什么）
   ↓ 推导
概念层（是什么）
   ↓ 推导
工程层（怎么实现）
   ↓ 落码
实现（具体代码）
```

## 九、入稿点（交叉引用）

每份文档结尾应列出「入稿点」：

```markdown
## 入稿点

- 哲学：`01-哲学/01-世界观.md`
- 决策：`03-决策/已定/260826-2240-传承殿-启动决策.md`
- 数据模型：`04-设计/数据模型/01-记忆.md`
```

## 十、复查清单

每份文档发布前必须自查：

- [ ] 有 H1 标题 + 一句话本质
- [ ] 概念文档有哲学层 + 概念层 + 工程层
- [ ] 决策文档有 8 个 YAML 字段
- [ ] 有 decided_by + falsifiable + implements
- [ ] 文档结尾标识符合本规范
- [ ] 入稿点列出依赖关系
- [ ] 不含过往实现的任何具体命名/编号/指代
- [ ] 不含借来的词（「乐高」、「工具 manifest」等）
