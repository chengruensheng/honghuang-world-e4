## 二、六层结构（分层的哲学依据）

为什么要分六层？因为**单链下沉、末端堆积**会让架构失效。六层每一层都承担真实切分。

```
维度 → 域 → 府 → 殿 → 阁 → 园
```

| 层 | 回答 | 职责 |
|:--|:--|:--|
| **维度** | 项目由什么构成 | 顶层模块分区 |
| **域** | 靠什么活着 | 语义分组（纯目录） |
| **府** | 什么能力 | crate（唯一编译单元） |
| **殿** | 哪些模块 | 模块分区 |
| **阁** | 什么功能 | 功能分组（方法契约 / 接口） |
| **园** | 怎么实现 | 实现落点（代码 / 存储 / 配置 / 模板 / 脚本 / 资源） |

### 切分纪律

- **拒绝单链**：府→殿→阁 的中间层不得只有一个子节点
- **均衡切分**：同一层兄弟节点的子节点数大致相当
- **准确切分**：按模块/功能真实语义边界，不硬凑数

## 三、4 分类抽象（4 类角色分工）

为什么是 4 分类而不是 13 角色？因为**抽象需要可机械判定**，具象只能靠 LLM 扮演。

| 分类 | 职责 | LLM 池 | 工具偏好 | 机械可判定 |
|:--|:--|:--|:--|:--|
| **决策者** | 化要求 / 派遣 / 最终裁决 / 定档 | 2-3 模型（多 LLM 投票） | 读记忆 + 提问 LLM + 规划 | 权限枚举 + 多 LLM 投票 |
| **设计者** | 设计 / 评审 | 3 模型（设计需要多样） | 读 + 检索类工具 | 写权限=假 + 评审四元组 |
| **验收者** | 验收（六维：前 4 维机械 + 后 2 维 LLM） | 1-2 模型 | 读 + 测试运行类 | 6 维中 4 维可机械测试 |
| **实现者** | 实现（按领域分工） | 1 模型 | 写 + 编辑 + 执行类 | 写权限=真 + 路径前缀校验 |

### 为什么不保留 13 角色

治理哲学基线 1：**确定性程序是治理操作唯一执行者**。13 角色全部依赖 LLM 扮演，无法机械判定。

13 角色做的事可以归约为 4 类职责（决策 / 设计 / 验收 / 执行），剥掉「名字」后只剩分类。

### 4 分类的工程优势

- **可证伪**：4 张角色卡，每张都有 falsifiable 条件
- **可机械判定**：权限 + 工具 + 路径前缀全部可枚举
- **可多 LLM 投票**：每分类独立 LLM 池，互不干扰
- **可审计**：每分类行为可独立统计

## 四、流水线（不可跳层不可反序）

为什么不可跳层？因为**因果方向不可逆**。

```
决策者 ─→ 设计者 ─→ 实现者 ─→ 验收者 ─→ 决策者（最终裁决）
              ↑          │           │
              │  重做    │           │
              └──────────┘           │
                验收驳回 ─────────────┘
```

### 铁律

- **不可跳层**：决策者不能直接验收，验收者不能直接设计
- **不可反序**：实现者不能先于设计者设计
- **可循环**：验收者驳回 → 实现者重做 → 验收者复验（最多 N 轮，超出升级决策者）

### 哲学依据

- **尊重因果顺序**：决策 → 设计 → 实现 → 验收 是因果链，方向单一
- **恰到好处**：每层的职责边界明确，不重叠
- **明确边界**：不在流水线内做不在范围内的决策
- **定向调节**：循环回路允许失败补正，不笼统终止
- **力度适配阶段**：早期宽松（多 LLM 投票可降级为单 LLM），后期严格（验收前 4 维机械优先）
