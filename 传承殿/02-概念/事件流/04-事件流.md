## 一、哲学层（为什么）

为什么需要事件流？因为**没有事件流就没有治理**。

- 治理动作必须可追溯 → 每个动作必须留痕
- 治理决策必须可验证 → 每个决策必须可重放
- 治理历史必须不可篡改 → 每次写入必须哈希校验

治理哲学禁止条款 3：「所有治理操作必须写入事件流，留痕不可篡改」——这是**治理存在的必要条件**。

## 二、概念层（是什么）

### 3 类事件（接 DSH 模式）

```
Session 事件（持久化） ── append-only 事实源
Agent 事件（live） ── 拦截 in-flight 工作
Capability 事件 ── attach policy + adapter
```

### 与「事件总线」命名的差异

| 「事件总线」命名 | 事件流概念 |
|:--|:--|
|「事件总线」|「事件流 + 分类」，三类事件语义不同|
|「publish/subscribe」|「Waterfall + Serial」两种模式|
|「无哈希校验」|「frozen outcome」，每次写入必须哈希链|

### 三条铁律

1. **append-only**：事件只能追加，不能删除或修改
2. **哈希链**：每个事件包含上一个事件的哈希（链式）
3. **不可改**：写入后任何修改都会破坏哈希链

## 三、工程层（怎么实现）

### 数据模型

```rust
pub struct 事件 {
    pub id: 事件ID,
    pub 类型: 事件类型,        // Session | Agent | Capability
    pub 模式: 事件模式,        // Waterfall | Serial
    pub prev_hash: Hash,       // 上一个事件的哈希
    pub 内容: serde_json::Value,
    pub 决定者: String,        // decided_by
    pub 时间: Timestamp,
    pub hash: Hash,            // 当前事件的哈希
}
```

### 写入流程

1. 构造事件内容
2. 读取 prev_hash（最新事件的哈希）
3. 计算当前事件哈希 = sha256(prev_hash + 内容)
4. append 到 jsonl
5. 进程级互斥锁（防并发交错）

### 读取 / 验证流程

1. 从头扫描 jsonl
2. 逐个验证哈希链
3. 任一哈希不匹配 → 拒绝（frozen outcome 违规）
