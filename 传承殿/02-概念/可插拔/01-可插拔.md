## 一、哲学层（为什么）

游戏 Lego 的哲学：每个积木都是**自包含的** + **可拼接的** + **可替换的**。

为什么系统需要这种哲学？因为**单点修改会引发连锁反应**——如果核心代码不可替换，任何小改动都要重新理解全系统。

治理哲学「治理可演化」 + DSH「万物皆插件」是同一个哲学断言：**核心无特权，可挂载可替换**。

## 二、概念层（是什么）

### 三条铁律

1. **自包含**：每个插件自带状态 + 行为 + 接口，不依赖其他插件内部
2. **可拼接**：插件之间通过**契约**交互，不是通过代码共享
3. **可替换**：插件可整体替换而不影响其他插件（接口契约不变）

### 与「乐高」命名的差异

| 「乐高」命名 | 可插拔概念 |
|:--|:--|
|「乐高积木」|「插件单元」，必须能回答「为什么独立」|
|「拼接」|「契约交互」，必须有 manifest 描述接口|
|「替换」|「接口稳定」，必须保证外部行为不变|

### 错误用例

```rust
// 错误：直接使用"乐高"概念而未推导
fn 乐高积木_拼接(积木A: &积木, 积木B: &积木) { ... }

// 正确：先回答"为什么独立"再命名
fn 插件单元_契约交互(plugin: &dyn 插件契约, 其他: &dyn 其他契约) { ... }
```

## 三、工程层（怎么实现）

### Service Definition 机制

每个插件在 lib 根定义一个**服务 trait**，作为契约：

```rust
pub trait 插件契约: Send + Sync {
    fn 名称(&self) -> &str;
    fn 能力清单(&self) -> Vec<能力描述>;
    fn 调用(&self, 输入: 调用输入) -> Result<调用输出, 错误>;
}
```

### 插件注册表

- 插件上下文维护 `HashMap<TypeId, Arc<dyn 插件契约 + Send + Sync>>`
- 注册：`ctx.注册服务(服务实例)`
- 查找：`ctx.查找服务::<Arc<dyn 插件契约>>()`

### Manifest 契约（不是「工具 manifest」）

每个插件目录必须有 `manifest.{toml,json}`，描述：
- **名称**：插件唯一标识
- **接口**：实现哪些契约
- **依赖**：依赖哪些插件（可枚举）
- **副作用**：调用是否会修改外部状态
- **不可改**：调用结果是否 frozen outcome
