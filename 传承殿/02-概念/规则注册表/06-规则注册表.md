# 06-规则注册表.md

> **概念·法**——不是"RULE_REGISTRY"，是"治理规则必须可证伪可演化"。

## 一、哲学层（为什么）

为什么需要规则注册表？因为**没有单一真相源就没有规则演化**。

- 规则散落在 if-else → 修改需搜索全文 → 容易遗漏
- 规则集中在注册表 → 修改一处即生效 → 可证伪可演化

司衡工程哲学的核心理念：**规则作为治理的基本单元，其元数据（治理域、严格度）是规则的意图，应该显式声明而非隐含在控制流中**。

## 二、概念层（是什么）

### RuleEntry 结构

```rust
pub struct 规则条目 {
    pub 规则ID: String,           // 唯一标识
    pub 严格度: 严格度,           // Fatal | Warning | Info
    pub 治理域: 治理域,           // 前置 | 结构 | 引用 | 治理 | 派发
    pub 描述: String,             // 做什么
    pub decided_by: String,       // 谁定的
    pub falsifiable: Vec<可证伪条件>,
    pub implements: String,       // 哲学锚
}
```

### RULE_REGISTRY 单一真相源

```rust
pub const RULE_REGISTRY: &[规则条目] = &[
    // 14 条规则，按规则ID排序
    // 实际发射 violation 的规则才进注册表
    // "概念规则"（声明但不实际发射）不进注册表
] as const;

pub const RULE_COUNT: usize = RULE_REGISTRY.len();
```

### 与"RULE_REGISTRY"命名的差异

| "RULE_REGISTRY" 命名 | 规则注册表概念 |
|:--|:--|
|"常量数组"|"注册表 + 派生值"，RULE_COUNT 必须派生|
|"枚举 + 字符串"|"结构体 + 严格度枚举"|
|"无 decided_by"|"决策契约字段强制"|

### 三条铁律

1. **派生值不硬编码**：`RULE_COUNT = RULE_REGISTRY.len()`，无裸常量
2. **幽灵规则不进注册表**：只声明不发射的规则是"概念规则"，不入工程实现
3. **修改需新决策覆盖**：任何规则修改需新决策文档（带 falsifiable）

pub fn 评估接单(候选: &候选, RULE_REGISTRY: &[规则条目]) -> 接单决策 {
