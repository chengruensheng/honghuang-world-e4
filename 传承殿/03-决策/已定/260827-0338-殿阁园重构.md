# 殿阁园六层深化 + 目录命名合规

> **原语**：本项目沿用的创世叙事词汇，仅用于命名与溯源。
> **工程理解词语**：将原语翻译为可精确执行、可验证的工程术语；本文正文一律使用工程理解词语，原语仅在《术语对照表》中保留。
> 术语对照见 `传承殿/00-宪法/术语对照表.md`。
> 说明：`殿 / 阁 / 园` 是六层结构专名（工程语义见《术语对照表》3.5），正文按原字引用。

## 背景

v1.0.0 release 后，各 crate 均为平铺 `入口.rs` 单文件结构，目录命名用纯连字符（`基础设施-域`）。

对照 `00-宪法/开发遵守格式模板.md`：
- 域 = `XX-域`、府 = `XX-府`（连字符无空格）
- 府内 = `入口.rs + Y-殿/ + Z-阁/ + W-园/` 嵌套

当前结构两项均不满足。本次重构使代码结构符合规范，不改变任何对外行为。

## 方案

### 主方案：分两步

**第一步·目录命名合规**（全局，一次性）
- 同步更新 workspace Cargo.toml members + 各 crate Cargo.toml [lib] path
- 验证 cargo check + test

**第二步·殿阁园深化**（逐 crate，可并行）
- 仅对 > 200 行的 crate 拆分
- 小 crate（< 200 行）保持平铺（符合"简化 > 复杂"）
- 每个 crate：入口.rs 保留 pub mod + pub use，实现下沉到殿/阁/园
- 非 ASCII 模块名用 `#[path]` 桥接

### 备选方案 A：全部 crate 都拆殿阁园
- 不采纳：小 crate 拆分后每层只有 1-2 个小文件，违反"拒绝单链"反而增加认知负担

### 备选方案 B：只改目录命名不拆殿阁园
- 不采纳：规范明确要求府内嵌套，且大 crate 平铺已影响可读性

## 后果

### 正面
- 目录命名符合规范，新协作者可一键复制格式
- 大 crate 逻辑分殿/阁/园，可读性提升
- 为未来园级实现替换（可插拔）做好结构准备

### 代价与风险
- 风险 1：非 ASCII 模块名 `#[path]` 桥接写法错误导致编译失败 → 每 crate 拆完立即 cargo check
- 风险 2：拆分时 pub use 导出遗漏导致下游 crate 编译失败 → 拆完跑 workspace test
- 风险 3：目录重命名破坏 git 历史 → 用 `git mv` 保留 rename 检测
- 代价：全量 crate 重构工作量

## 可证伪条件验证

- 重构完成后立即跑一键全验，全绿即第一步通过
- grep 检查域/府目录命名，全部符合规范即第二步通过
- cargo test --workspace 全过即行为不变
