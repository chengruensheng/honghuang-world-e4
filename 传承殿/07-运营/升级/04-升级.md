# 04-升级.md

> **运营层·升级**——版本演进与依赖更新。

## 一、哲学层（为什么）

为什么需要明确的升级流程？因为**不升级 = 累积技术债**。

- 升级太频繁 → 风险高
- 升级太慢 → 累积技术债
- 无流程 → 升级靠记忆 → 遗漏

司衡顺势（力度适配场景）：早期宽松升级，后期严格升级。

## 二、概念层（是什么）

### 升级分类

| 升级类型 | 风险 | 频率 | 流程 |
|:--|:--|:--|:--|
| **补丁升级**（patch） | 低 | 每周 | 自动 |
| **小版本升级**（minor） | 中 | 每月 | 人工 + 门禁 |
| **大版本升级**（major） | 高 | 每季 | 决策文档 + 试点 |

### 升级三原则

1. **门禁必过**——升级前必过一键全验 10 项
2. **版本回溯**——每次升级必须有 tag + 决策文档
3. **试点先行**——大版本先在非生产环境试点

## 三、工程层（怎么实现）

### 补丁升级（自动）

```bash
# 自动检测 + 升级
cargo update --aggressive
cargo test --workspace --lib
cargo clippy --workspace -- -D warnings
cargo build --release

# 全过则提交
git add Cargo.lock
git commit -m "chore(deps): 自动补丁升级"
```

### 小版本升级（人工）

```bash
# 1. 升级前门禁
bash 一键全验.sh
if [ $? -ne 0 ]; then echo "✗ 门禁未通过，禁止升级"; exit 1; fi

# 2. 决策文档
#   创建 03-决策/已定/YYMMDD-HHMM-{slug}.md
#   decided_by + falsifiable + implements

# 3. 升级依赖
cargo update {crate_name}@{version}

# 4. 验证
cargo test --workspace --lib
bash 一键全验.sh

# 5. 提交 + tag
git tag v{minor}.{patch}
```

### 大版本升级（决策 + 试点）

```bash
# 1. 决策文档（必须经界主拍板）
#   创建 03-决策/已定/YYMMDD-HHMM-{slug}.md
#   包含：
   #   - 升级目标版本
   #   - 升级风险评估
   #   - 试点环境 + 试点周期
   #   - 回滚预案

# 2. 试点环境升级 + 验证
cargo update {crate_name}@{major}
bash 一键全验.sh
cargo test --workspace --lib

# 3. 试点周期（建议 1 周）

# 4. 生产环境升级（接 07-运营/部署/01-部署.md）

# 5. 提交 + tag
git tag v{major}.{minor}.{patch}
```

### 升级记录

每次升级都必须有决策文档（`03-决策/已定/`）——升级本身是治理动作。

- 部署：`07-运营/部署/01-部署.md`
- 决策：所有升级决策入 `03-决策/已定/`
