# 01-部署.md

> **运营层·部署**——从源码到运行实例的具体落地。

## 一、哲学层（为什么）

为什么需要明确的部署流程？因为**部署是治理动作的可观察起点**。

- 无部署文档 → 每次部署靠记忆 → 容易遗漏
- 有部署文档 → 每次部署走流程 → 可审计可回滚

司衡基线 4（可验证性约束）：操作可追溯。部署也是操作，必须留痕。

## 二、概念层（是什么）

### 三条铁律

1. **版本化部署**——每个部署必须有版本号（commit hash 或 tag）
2. **可回滚**——任何部署都必须能在 5 分钟内回滚
3. **可观测**——部署后立即可观测（健康检查 + 日志）

### 部署形态

| 形态 | 适用场景 | 回滚时间 |
|:--|:--|:--|
| **编译产物部署** | 生产环境 | < 1 分钟（替换二进制） |
| **源码部署** | 开发环境 | < 30 秒（cargo build） |
| **容器部署** | 多节点 | < 5 分钟（重启容器） |

## 三、工程层（怎么实现）

### 部署前检查

```bash
# 一键全验 10 项必须全绿
bash 一键全验.sh
if [ $? -ne 0 ]; then
  echo "✗ 门禁未通过，禁止部署"
  exit 1
fi

# 检查 git 状态
git status --porcelain | grep -q . && echo "⚠ 有未提交修改"
git log -1 --oneline  # 当前 commit
```

### 部署步骤

1. **预编译**：`cargo build --release`
2. **备份**：当前运行的二进制复制为 `target/release/命令操作.bak`
3. **替换**：新二进制覆盖 `target/release/命令操作`
4. **重启**：kill 旧进程 + 启动新进程（systemd 或 supervisor）
5. **健康检查**：`./命令操作 --health` 退出码 0
6. **观测**：日志 + 监控指标
