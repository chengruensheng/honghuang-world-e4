# 03-司衡-收敛机制.md

> **参考资料**——司衡（sgmov/sihankor）「收敛机制」专题摘要：从四道哲学锚定到四段收敛闭环的完整链路。本文对 01-司衡仓库 作专题深化，聚焦「司衡到底靠什么把发散收拢」。

## 一、一句话收敛定义

> 司衡 = 一个承认治理自身也不完备的代码工程收敛引擎。发散是「自-然」（自己如此，不需人推动）；收敛是「必-为」（必须人为、持续、系统施加）。无治理则无收敛。

收敛不是默认方向。司衡的全部机制，都是为「必-为」这一规范性要求提供工程抓手。

## 二、收敛的哲学根：四道（道一～道四）

来源：`docs/specs/philosophy/Tao-On-Natural-Convergence.sih.md`（id 260627-1100，stage 3/3）。

| 道 | 陈述 | 认识论标签 | 外部锚定 |
|:--|:--|:--|:--|
| 道一 | 发散自-然，收敛必-为 | external-anchor | 热力学第二定律（熵增自-然，局部熵减需做功） |
| 道二 | 意图先于代码，因果方向不可逆 | design-corollary | 无直接锚定（结构类比时间之矢） |
| 道三 | 凡编码皆为意图之有损编码（代码自晦、意图必复） | external-anchor | Shannon 信息论（编码必有损，意图恢复需额外信息） |
| 道四 | 规约与实现必有间隙 | 道四a：tautology；道四b：empirical-hypothesis | 道四a 锚定 Gödel 不完备性定理；道四b 为可证伪经验假设 |

关键结构：前三道构成「意图发散 → 有损编码 → 代码自晦 → 意图恢复 → 再发散」的闭合循环；道四是自我指涉轴，把「治理者也会出错」递归应用于治理自身。**道四b 指出：间隙随时间增大，且增大速率与规则数量正相关**——这是司衡「规则要稀缺、要定期修剪」的哲学根据。

## 三、收敛的四段闭环（工程机制）

来源：README.md 概述 + `src/mind/grilling.rs` + `src/mind/ict.rs`。

1. **追问收敛（上游）**：GrillingEngine 在 Mind 三机（iCL 认知 / iWW 决策 / iCT 验证）之前运行，用元规则驱动的四问把自然语言意图收敛为结构化提示词。
2. **约束注入（生成前）**：把 validator 已知规则前置注入提示词，外部 Agent 在生成文档之前就知道规则，减少生成后再修正的次数。
3. **产出验证（生成后）**：六域 F/G/J validator（22+ 规则）+ iCT 方圆机五法检验。
4. **修正闭环（再生成）**：复用既有 validator 驱动再生成，不新增修正逻辑（知止：不重复造轮子）。

### 3.2 追问引擎的核心自律：验证者与生成者分离

来源：`docs/decisions/260622-1325-grilling-engine-decision.sih.md` 的「备选方案 B」拒绝理由。

> 追问引擎**不自调 LLM**。若追问引擎持有 API key、自己调 LLM 生成内容，则违反司衡核心定位（司衡不生成代码/文档，只验证），且「验证者与生成者做在同一进程内，鉴的公信力减弱」。

追问引擎只生成**提示词**，由外部 Agent 消费（MCP tool `sihankor_propose`）。

来源：`grilling.rs` 的 `inject_constraints()`。注入的已知约束包括 V-F-01/03/04/05/06/07、V-G-02/03/04/05/06/09、V-J-01、C-01（字符替换：em-dash → fullwidth colon 等）。nature=decision 时追加 V-G-09（decisions/ 目录文档 stage ≥2/3 必须有 decided-by 字段）。

### 3.4 iCT 五法验证

来源：`src/mind/ict.rs`。对 decision_proposal 逐法判定并产 overall verdict：

- **顺因**：逆写检查（上游改动）、越级检查（跳过 stage）、引用方向。
- **有度**：力度不足 / 力度过度。
- **知止**：不判断哲学对错、不修改非 .sih.md 文件、不管理 drafts/。
- **损补**：损补方向反置、对同一文档同时 merge 与 archive 的冲突。
- **顺势**：措辞匹配、root 保护、环检测、archive 文档。

## 四、两层状态机（收敛的推进骨架）

来源：`src/core/project_state.rs` + `docs/decisions/260625-0301-pipeline-state-machine-decision.sih.md`。

| 层 | 载体 | 职责 |
|:--|:--|:--|
| 文档层 | Document.stage | 1/3 提案 → 2/3 审阅 → 3/3 拍板 |
| 项目层 | ProjectState（持久化 .sih/project.json） | suggest_next_action 推导下一步 |

推进规则：
- **追问收敛后自动 2/3 起步**（顺因：追问就是收敛动作，收敛后产物不应还是 1/3）。
- **upstream 全部 ≥2/3 后才提示推进**（顺势：不自动推进，留人确认）。
- suggest_next_action 规则优先级：Rule 0 待处理合道修正任务 > Rule 1 待确认检查点 > Rule 2 上游已就绪的 1/3 文档可推进 > Rule 3 无 decision 的 2/3 proposal > Rule 4 stage 推进提示。

## 六、对传承殿的承接与启示（本项目所需参考）

已承接（见 01-司衡仓库 §九）：5 工程基线、4 禁止条款、追问引擎 4 问题、规则注册表；元三治待 Phase 4。

本文新增可吸收的语义：

1. **认识论标签制度**（external-anchor / empirical-hypothesis / tautology / design-corollary）——可对应传承殿决策契约 `falsifiable` 的三分类（机械判定 / 人工统计 / 文档审查），为每条规则标注「权威来自哪里、能被什么推翻」。
2. **两层状态机与角色流水线互补**——司衡的 stage 是「文档成熟度」1/3→3/3，传承殿的流水线是「角色分层」道祖→圣人→大罗→准圣→道祖终裁。二者语义不同、可叠加：文档成熟度可叠加在角色流水线之上。
3. **iCT「逐法判定 + overall verdict」结构**——可借鉴到传承殿准圣级验收的六维验收：逐维判定 + 总判，而非笼统通过/不通过。
4. **道四b 支撑「格位稀缺 + 文档收割门」**——规则越多、间隙越大；传承殿已定决策「格位稀缺 36 上限」「文档收割门防污染」正是道四b 的工程落地。
5. **验证者与生成者分离的机制化**——追问引擎不持 API key，对应传承殿「验证分离」概念；进一步可借鉴「约束注入」：验收规则前置注入生成提示词，减少打回轮次。
