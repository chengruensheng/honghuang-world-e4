## 三、实施任务（7 天）

### Day 1-2：模型连接-府（moxing_fu）新建 crate

- 新建 `鸿蒙/基础设施 - 域/模型连接 - 府/`（moxing_fu）
- 实现 `模型连接` trait：
  - `POST(endpoint, payload) -> Result<Response, Error>`
  - `配置注入()`：从 .env 读 API key / endpoint
  - `流式输出()`：支持 SSE（如 OpenAI / DeepSeek）
- `请求` struct：model + messages + temperature + tools
- `响应` struct：content + tool_calls + usage
- 引入依赖：`ureq = "2"`（轻量 HTTP 客户端，无 TLS 依赖）
- 4 分类 LLM 池：`LLM池条目` 列表，按 `角色卡.LLM池` 字段选择

**单元测试**：mock HTTP server + 解析响应 + 错误重试。

### Day 3-4：5 类工具实现

- `工具清单`：5 类枚举（探查 read / 编辑 write / 执行 run / 版本 git / 编排 plan）
- `工具` trait：
  - `名称() -> &str`：工具名
  - `执行(input: 调用输入) -> Result<调用输出, Error>`
  - `描述() -> &str`：供 LLM 看到
- 工具 manifest.json：`{name, description, parameters, returns}` 5 个工具
- 任务执行-府 扩展：`工具调用循环` —— LLM 返回 tool_calls 时调用工具

**单元测试**：每个工具 mock 调用 + 工具清单枚举完整。

### Day 5-6：4 分类 LLM 池 + 端到端

- `分类_角色卡`（已实现）扩展：每张卡绑定具体 LLM endpoint
- `任务执行` 新增 `LLM 调用` 函数：选 LLM → 构造 prompt → POST → 解析响应 → 返回
- 端到端 e2e：CLI run "修复 typo" → 任务经 4 分类 LLM 各调用一次
- 集成测试覆盖率 ≥ 80%

**e2e 验证**：用真实 LLM 跑 1 个简单任务（可 mock 服务器，不调真实 API）。

## 七、风险与回滚

- **风险 1**：ureq 不支持流式 → 阶段 7 用 polling 而非 streaming；阶段 8+ 改用 async + reqwest
- **风险 2**：deny.toml 加 ureq 后 license 不匹配 → ureq 用 MIT/Apache-2.0；待实施时确认
- **风险 3**：4 分类 LLM 池配置不当导致 e2e 失败 → 默认都指向同一 mock 服务器，单元测阶段验证配置
